TutorTrack API guide

Connect your own systems to TutorTrack with the REST API and webhooks.

Last updated: 2026-10-21 · API version v1

Overview

The TutorTrack API is the same REST API that the TutorTrack apps use. A subset of it is public: those endpoints accept API keys and OAuth access tokens and are listed in the endpoint reference. Everything else is internal to the first-party apps and refuses tokens.

WhatWhere
Base URLhttps://app.tutortrack.app/api/v1/ (local development: http://localhost:8010/api/v1/). The token identifies your organisation, so any TutorTrack host works.
Interactive reference/api/v1/docs/
Public OpenAPI documentGET /api/v1/developer/openapi.json, or Download OpenAPI in Developer › API documentation
Postman collectionGET /api/v1/developer/postman.json, or Download Postman collection
ChangelogGET /api/v1/developer/changelog, and the Changelog on the documentation page

All requests and responses use JSON over HTTPS. Requests without a token, or with a token for the wrong organisation, never see another organisation's data: every query runs inside the token's organisation, enforced by the database.

Quick start

  1. In the admin app open Developer › API keys and select Create key. You need the developer.apikey.manage permission (owners and admins have it).
  2. Give the key a name, choose its scopes (for example clients:read), and optionally a branch, an expiry date and an IP allowlist.
  3. Copy the key. It starts with ttk_ and is shown once; TutorTrack stores only a hash.
  4. Call the API with the key as a bearer token:
curl https://app.tutortrack.app/api/v1/clients \
  -H "Authorization: Bearer $TUTORTRACK_API_KEY"
import requests

r = requests.get(
    "https://app.tutortrack.app/api/v1/clients",
    headers={"Authorization": f"Bearer {api_key}"},
    params={"page_size": 100},
)
r.raise_for_status()
for client in r.json()["results"]:
    print(client["display_name"])
const res = await fetch("https://app.tutortrack.app/api/v1/clients", {
  headers: { Authorization: `Bearer ${apiKey}` },
});
const { results, next } = await res.json();

Authentication

Send Authorization: Bearer <token> on every request. There are two kinds of token:

API key ttk_…

For your own scripts and back-office integrations in one organisation.

OAuth access token tta_…

For apps that other organisations connect, through the OAuth 2 authorisation code flow.

A token acts as the person who created it (an API key) or who approved the app (an OAuth grant). A request is allowed only when both hold:

  • the endpoint is public and the token has a scope for its resource (read for GET, write otherwise; write implies read); and
  • the person still has the permission the endpoint needs, and is still an active member of the organisation.

So a token can never do more than its owner. Field-level permissions apply too: a key made by someone who cannot see contact phone numbers gets responses without them.

API keys

  • Format: ttk_<12-character prefix>_<48 hex characters>. The prefix is shown in the key list so you can tell keys apart.
  • Branch: a key can be limited to one branch; it then sees only that branch's records.
  • IP allowlist: optional list of addresses or CIDR ranges. Requests from other addresses get 401.
  • Expiry: optional. Expired keys get 401.
  • Rotation: Rotate issues a new key with the same settings. The old key keeps working for an overlap period (organisation setting developer.api_key_rotation_overlap_hours) so you can deploy the new one.
  • Revocation: takes effect immediately.
Keep keys secret

Never put an API key in a browser or mobile app. Use OAuth with PKCE for public clients instead.

OAuth 2 apps

Register an app in Developer › Apps. A confidential app (a server) gets a client secret; a public app (a single-page or mobile app) has none and must use PKCE. TutorTrack supports the authorisation code grant with PKCE (S256) and refresh tokens.

EndpointUse
/api/v1/oauth/authorizeSend the user here with client_id, redirect_uri, response_type=code, scope (space-separated), state, code_challenge and code_challenge_method=S256. The user signs in and approves the scopes on a consent screen; TutorTrack then redirects to redirect_uri with code and state.
POST /api/v1/oauth/tokengrant_type=authorization_code (with code, redirect_uri, code_verifier) or grant_type=refresh_token. Confidential clients also send client_secret.
POST /api/v1/oauth/revokeRevoke an access or refresh token.
  • Authorisation codes last 10 minutes and work once.
  • Access tokens (tta_…) last one hour by default (expires_in in the token response).
  • Refresh tokens (ttr_…) last 90 days and rotate on every use. If a used code or refresh token is presented again, TutorTrack treats it as stolen and revokes every token of that grant.
  • Admins see connected apps under Connected apps in Developer › Apps and can disconnect them; every token of the app then stops working.
  • PKCE is mandatory for public clients and recommended for confidential ones.

Requests and responses

Data types

  • IDs are UUIDs (time-ordered UUIDv7).
  • Timestamps are ISO 8601 in UTC, for example 2026-10-14T09:30:00Z. Lessons, users, branches and the organisation also carry an IANA timezone; recurring lessons repeat in the lesson's local time.
  • Money is an object with a decimal string and an ISO 4217 currency: {"amount": "40.00", "currency": "GBP"}. Never send money as a float.
  • Financial records (invoices, payments, credit notes) cannot be edited or deleted once issued. Correct them with credit notes and adjustments.

Pagination

Lists use cursor pagination, newest first. The response has results, next and previous; follow next until it is null. Use page_size to change the page length (default 50, maximum 200). Cursors are opaque: do not build them yourself.

{
  "next": "https://app.tutortrack.app/api/v1/clients?cursor=cD0yMDI2LTEw...",
  "previous": null,
  "results": [ { "id": "0192…", "display_name": "The Patel family", … } ]
}

Errors

Errors are RFC 7807 problem details with content type application/problem+json. Validation errors list messages per field under errors. Quote request_id when you contact support.

{
  "type": "https://docs.tutortrack.app/problems/validation-error",
  "title": "Invalid input.",
  "status": 422,
  "detail": "…",
  "errors": { "email": ["Enter a valid email address."] },
  "request_id": "01J…"
}
StatusMeaning
400 / 422The request is malformed or fails validation or a business rule.
401The token is missing, invalid, expired, revoked, or used from an address outside its allowlist.
403The token lacks the scope, or its owner lacks the permission, or the endpoint is internal.
404The record does not exist in your organisation (or branch, for a branch key).
409A conflict, for example a request with the same Idempotency-Key is still running.
412 / 428The If-Match ETag is stale, or the endpoint requires one.
429Rate limit exceeded; wait for Retry-After seconds.
5xxOur fault. Retry with backoff; POSTs are safe to retry with an Idempotency-Key.

Idempotency

Send an Idempotency-Key header (a UUID works well) on POST requests to make them safe to retry for 24 hours. Financial POSTs (payments, invoices, charges, payment requests) should always send one.

  • Same key, same request: the stored response comes back with Idempotent-Replayed: true.
  • Same key, different body: 422 idempotency-key-reused.
  • Same key while the first request is still running: 409 idempotency-request-in-progress.
  • Server errors (5xx) are not stored, so a retry runs the request again.

Keys are scoped to your organisation and token.

Concurrent updates

Some resources return an ETag. Send it back in If-Match on PUT/PATCH to make sure nobody changed the record since you read it. A stale ETag gets 412; endpoints marked If-Match in the reference accept it, and some require it (428 without it).

Rate limits

Each token may make 600 requests a minute, with bursts of up to 100 a second. Every response carries X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset (Unix seconds). Over the limit you get 429 with Retry-After. Need more? Ask your TutorTrack contact: limits can be raised per organisation.

Versioning and deprecation

The major version is in the URL (/api/v1/). Within v1 we only add fields, endpoints and event types, so ignore fields you do not know. An endpoint that is going away sends Deprecation (RFC 9745), Sunset (RFC 8594) and a Link to its changelog entry on every response, months before removal.

Files on public forms

Enquiry forms and job openings can have file fields. If you post a form from your own site, upload each file first. These endpoints need no token; call them on the organisation's address. They are limited to 60 requests an hour per IP address.

  1. POST /api/v1/public/uploads with target (form or opening), the form's or opening's slug, the field's kind (document, cv or video), filename, content_type and size_bytes. The form must be published and have a file field of that kind. The reply has a token and an upload (a presigned URL, method and headers, valid for 15 minutes).
  2. Send the bytes to upload.url with upload.method and upload.headers.
  3. POST /api/v1/public/uploads/complete with the token. Size, type and the file's first bytes are checked (a mismatch is refused with upload_mismatch), and the malware scan is queued.
  4. Send the token (or a list of tokens for a field that takes several files) as that field's answer in POST /api/v1/public/forms/{slug} or POST /api/v1/public/job-openings/{slug}. A token works once, for that form, for 24 hours.

Limits: documents and CVs up to 10 MB (PDF, Word; documents also JPEG, PNG, WebP, HEIC), videos up to 100 MB (MP4, MOV, WebM). Errors use the usual problem format with a code: uploads_not_accepted, file_type_not_allowed, file_too_large, upload_mismatch, upload_token_invalid, upload_claimed, upload_incomplete.

Matching needs, waitlist suggestions and classroom resources

  • Students' needs in matching. Students have exam_boards, sen_tags and tutor_gender_preference; tutors have exam_boards, sen_tags and gender. SEN tags and the gender preference are only returned to callers with people.student.view_sensitive, a tutor's gender only with people.tutor.view_sensitive; without them the fields are left out and can't be written. POST /api/v1/matching/search takes the job's students' needs, or exam_boards, sen_tags and gender to override them; the reply's needs says what was used and whether gender preferences are on (matching.gender_preference; when off, the gender is ignored). The breakdown gains exam_board and sen only when a search asks for them.
  • Waitlist suggestions. GET /api/v1/waitlist-suggestions (status: open by default, offered, dismissed, closed or all; entry) lists tutors who have room for waiting students. POST …/{id}/offer (optional details and hours) sends the family the offer link; POST …/{id}/dismiss stops that tutor being suggested for that student. The webhook event waitlist.suggestion_created carries ids and the reason only.
  • Classroom resources. GET /api/v1/lessons/{id}/classroom returns each resource's kind, media_type, message and shared_at; POST /api/v1/lessons/{id}/classroom/resources/{resource_id}/open gives anyone in the classroom a link to a resource shared with the lesson (a short-lived link for files).
  • Scheduled progress reports. The webhook event progress_report.batch_drafted (counts only) fires once per period when the organisation's schedule drafts reports.

Webhooks

Webhooks tell your system when something happens in TutorTrack, so you do not have to poll. TutorTrack sends an HTTPS POST with a JSON body to your endpoint for each event it is subscribed to.

Setting up an endpoint

  1. Open Developer › Webhooks and select Add endpoint (permission developer.webhook.manage).
  2. Enter the HTTPS URL. Private and internal addresses are refused.
  3. Choose the events: individual types such as lesson.completed, or every event of an aggregate with a wildcard such as lesson.*. There is no global wildcard.
  4. Copy the signing secret (whsec_…, shown once) into your receiver.
  5. Select Send test event to deliver a webhook.test event and check your receiver.

You can also manage endpoints through the API with the webhooks:write scope (see Webhooks in the reference). GET /api/v1/webhook-event-types lists every event type with its payload fields, and /api/v1/webhook-event-types/{type}/sample returns an example.

Payload

Each delivery has these headers:

HeaderValue
Webhook-IdThe event ID. Stays the same across retries and redeliveries: use it to drop duplicates.
Webhook-EventThe event type, for example invoice.issued.
Webhook-Attempt1 for the first attempt, then 2, 3, …
Webhook-Signaturet=<unix seconds>,v1=<hex HMAC> (see below).
User-AgentTutorTrack-Webhooks/1

  • For sensitive aggregates (message, thread, recording, background_check) the payload carries IDs and status only. Fetch the record through the API if your token may see it.
  • Safeguarding, privacy casework, security and AI internals never produce webhooks.

Verifying signatures

Compute HMAC-SHA256 with your endpoint secret over the timestamp, a full stop and the raw request body, compare it with each v1 value in constant time, and reject timestamps more than five minutes from your clock. While a rotated secret overlaps (24 hours), the header has a second v1 for the old secret.

import hashlib, hmac, time

def verify(secret: str, header: str, body: bytes, tolerance: int = 300) -> bool:
    parts = [p.split("=", 1) for p in header.split(",")]
    t = next(int(v) for k, v in parts if k == "t")
    if abs(time.time() - t) > tolerance:
        return False  # outside the replay window
    expected = hmac.new(secret.encode(), f"{t}.".encode() + body, hashlib.sha256).hexdigest()
    return any(hmac.compare_digest(expected, v) for k, v in parts if k == "v1")
import { createHmac, timingSafeEqual } from "node:crypto";

export function verify(secret, header, rawBody, tolerance = 300) {
  const parts = header.split(",").map((p) => p.split("="));
  const t = Number(parts.find(([k]) => k === "t")[1]);
  if (Math.abs(Date.now() / 1000 - t) > tolerance) return false;
  const expected = createHmac("sha256", secret).update(`${t}.`).update(rawBody).digest("hex");
  return parts.some(([k, v]) => k === "v1" &&
    timingSafeEqual(Buffer.from(v), Buffer.from(expected)));
}

Delivery and retries

  • Reply with any 2xx within 10 seconds. Do slow work after you reply.
  • Failed deliveries are retried with exponential backoff: 15 attempts over about 72 hours.
  • An endpoint that keeps failing for three days is disabled and the organisation's admins are notified. Fix the receiver, then select Enable in Developer › Webhooks.
  • Events can arrive out of order and more than once. Order by occurred_at and de-duplicate on Webhook-Id.
  • The delivery log keeps every attempt (request, response status, timing) for 30 days. Select Redeliver on any delivery to send it again with the same Webhook-Id.
  • Rotate secret issues a new secret; the old one stays valid for 24 hours.

Zapier, Make and sandboxes

  • Zapier and Make: TutorTrack publishes app definitions for both platforms (/api/v1/developer/connectors/zapier and …/make). They use OAuth, trigger on webhook events and act through the public API.
  • Sandboxes: Developer › Sandboxes creates up to three sandbox organisations filled with sample data. Build and test against a sandbox, then switch the key or OAuth connection to your live organisation.
  • Marketplace: published integrations are listed in Settings › Marketplace, where admins connect them.
