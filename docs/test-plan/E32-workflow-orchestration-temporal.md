# E32 — Workflow Orchestration (Temporal): manual tests

**Scope.** The Temporal runtime as seen by testers and operators: the dev server and worker, tenant-prefixed workflow ids and search attributes, the outbox → workflow bridge, payload encryption and the codec endpoint, tenant-local timers, per-organisation Schedules (paused on suspension), the processes API and the Process timeline, terminate/restart for platform staff, resilience to worker restarts — and, for each of the 58 workflows in the codebase, what starts it, what a person sees and how to inspect it. The business behaviour of each process is tested in its own epic file; this file checks the orchestration. Spec: [E32](../epics/E32-workflow-orchestration-temporal.md); pattern in [02-architecture.md §9](../02-architecture.md).

**Built differently from the spec (Implementation notes win):**
- Runtime lives in `tutortrack/core/workflows/`; the `workflows` app holds the processes API, codec endpoint, worker command and `DemoReminderWorkflow` (kept as the template).
- Start reuse policy `ALLOW_DUPLICATE_FAILED_ONLY`: a duplicate start returns nothing; signals to finished or unknown workflows are ignored.
- The Process timeline component is shown on Settings (organisation closure). Other records show process state through their own screens (pay runs, imports, DSARs…). The platform console has no processes page: terminate/restart are API calls (`POST /api/v1/processes/<id>/terminate|restart`, platform staff, reason required).
- KMS-managed payload keys come from E29; locally a dev default AES-GCM key is used.

**Common preconditions.**
- `make infra` (Temporal dev server: gRPC `localhost:7233`, UI http://localhost:8233, namespace `tutortrack-local`, search attributes `OrganisationId`, `BranchId`, `SubjectType`, `SubjectId`, `TutorTrackProcess`).
- Worker: `cd backend && uv run python manage.py temporal_worker --task-queue all` (queues `default`, `billing`, `payroll`, `comms`, `integrations`, `imports`, `privacy`). With docker-compose, the `temporal-worker` service also runs `ensure_platform_schedules` first.
- Celery worker running (it dispatches the outbox that starts and signals workflows).
- **Finding a workflow:** Temporal UI → Workflows → query, for example `TutorTrackProcess="invoice-dunning"` or `OrganisationId="<org uuid>"`. Workflow ids are `<process>:<org uuid>:<subject id…>`. CLI: `docker compose exec temporal temporal workflow list --namespace tutortrack-local --query 'TutorTrackProcess="pay-run"'`, `... workflow describe --workflow-id <id>`.
- **Payloads are encrypted.** To read inputs in the UI, set the UI's codec server to `http://localhost:8010/temporal-codec` with "include cross-origin credentials", while signed in as platform staff on localhost:8010 (`TEMPORAL_CODEC_CORS_ORIGINS` includes http://localhost:8233). Without it, payloads show as encrypted binary.
- **Skipping time:** the dev server can't skip time. Durations are read from tenant settings at workflow start, so shorten the setting first (e.g. reminder days, grace minutes, link expiry), then start the process. Use the product's own "now" actions where they exist (Retry now, Recalculate now, Purge now, Issue statements, trigger a Schedule from the UI's Schedules page). Don't send signals with the Temporal CLI (inputs must be encrypted); use the app's buttons or API.
